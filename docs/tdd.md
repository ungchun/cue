# TDD 사이클

cue의 모든 코드 변경은 이 사이클을 따른다.

## red → green → refactor → green

흔히 "red-green-refactor"라 부르지만 정확히는 **네 단계**다.

| 단계 | 할 일 | 왜 |
|---|---|---|
| **red** | 테스트를 먼저 추가하고 실행한다. **실패를 확인한다.** | 처음부터 통과하면 잘못된 테스트를 짠 것이다 |
| **green** | 최대한 빨리 통과시킨다. **전체 테스트**를 돌린다 (새 테스트만 X) | 이번 변경이 다른 곳을 깨지 않았음을 확인 |
| **refactor** | 수정한 코드 + 그 주변 설계를 개선한다 | 코드 품질이 점진적으로 좋아지게 |
| **green** | **전체 테스트**를 다시 돌린다 | 리팩토링이 무언가 깨뜨리지 않았는지 확인 |

## 리듬

한 바퀴 **30초~5분**이 일반적이다. 너무 짧게 느껴져도 그게 정상이다.
한 바퀴가 **10분을 넘으면** → red로 돌아가 요구사항/테스트를 더 잘게 쪼갠다.

## 버그 수정 변형

버그일 때는 사이클이 달라진다:

| 단계 | 할 일 |
|---|---|
| **red** | 그 버그 때문에 **실패하는 테스트**를 만든다 → 버그가 재현 가능함 + 테스트로 고정됨 |
| ~~green~~ | 땜질용 빠른 green은 생략 |
| **refactor** | 버그가 있던 코드 주변의 품질을 개선한다 → 이 과정에서 버그가 고쳐진다 |
| **green** | 전체 테스트로 회귀(regression) 없음 확인 |

**왜 이렇게**: 버그는 그 자체로 문제이기도 하지만, 더 깊은 설계·품질 문제의 *증상*인 경우가
많다. 주변 품질을 개선하면 근본 원인을 일부 완화하게 되어, 한 번 잡힌 버그가 다시
나타나는 **regression을 근본적으로 막는다.**

## 에이전트의 약점 (주의)

- ⚠️ **refactor를 건너뛰기 쉽다.** 추상적으로 "개선하라"고만 하면 안 한다.
  구체적 체크리스트는 [docs/workflow/refactor.md](workflow/refactor.md) 참고.
- ⚠️ **테스트 코드 자체가 틀릴 수 있다.** 한 세션이 짠 테스트는 **새 세션 2~3회**로
  교차 검증한다 — 그 테스트가 정말 옳은지 독립적으로 확인한다.
- ⚠️ **green에서는 전체 테스트를 돌린다.** 새 테스트만 돌리면 부작용을 못 잡는다.
