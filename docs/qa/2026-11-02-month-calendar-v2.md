## 성능 (xctrace·lldb·footprint·leaks, 시뮬 Debug 빌드)

절대 ms는 맥 CPU 기준이라 실기기와 다르다. 같은 조건에서 비교한 값이다.

| 질문 | 결과 |
|---|---|
| 10년치를 미리 조회하나 | 아니다. 진입 시 일정 조회 3회(이번 달 ±1)와 할일 1회. 스와이프가 멈출 때마다 EventKit 조회는 약 1회(새로 들어온 이웃 달). 24달을 연속으로 넘겨도 조회 23회 |
| 같은 달을 다시 조회하나 | 윈도우(보이는 달 ±2) 안에서는 다시 조회하지 않는다. 윈도우 밖으로 나간 달은 비우고, 다시 오면 조회한다 |
| 스와이프 반복 시 메모리 | footprint가 48→50→51→58 MB로 오른 뒤 58 MB에서 평탄(24달 왕복을 3회 더 해도 그대로). 144회 이상 스와이프해도 같은 수준 |
| 누수 | `leaks` 0 |
| 스와이프 중 메인 스레드 | Hangs 0. 런루프 1회 최대 약 32~36 ms(Appium 접근성 조회 포함) |
| 스와이프 1회당 다시 그리기 | Page.body 약 2회, WeekRow 약 5회, ScheduleMonthView.body 1회. 다른 달 페이지는 다시 그리지 않음 |
| 첫 진입(콜드) | 월 모드로 처음 들어갈 때 런루프 1회 337~352 ms(타임라인 185 ms). 웜 진입은 33~38 ms |
| 241페이지 비용 | A/B 비교를 위해 25페이지로 줄인 빌드를 따로 만들었더니 콜드 진입이 263 ms였다. 따라서 페이지 수 몫은 약 75~90 ms이고 앱을 켠 뒤 첫 진입 1회에만 든다. 원래 범위(±120)로 되돌린 빌드에서 QA했다 |

- 화면 밖 페이지 모델은 TabView가 방문한 달마다 하나씩 붙잡고 있지만, 윈도우를 벗어나면 데이터를 비운다. 그래서 위 메모리 평탄화와 맞는다.

## 종합

- 데이터는 보이는 달 ±1만 조회한다. 디스크 스냅샷에는 기준 달 ±1만 남고, 지나쳐 간 달이나 멀리 점프한 달은 남지 않는다.
- 남은 UX 뉘앙스(미수정): 휠이 아직 감속하는 중에 체크마크를 누르면 마지막 값이 아니라 직전 값으로 이동할 수 있다. UIDatePicker가 값 변경을 멈춘 뒤에 알려 주기 때문이다.
- 피커 이동은 Done 경로 하나뿐이고, 범위 끝은 휠(min/max)과 페이저 양쪽에서 막힌다.
