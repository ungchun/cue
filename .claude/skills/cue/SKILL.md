# cue — 개발 하네스

cue의 모든 코드 변경을 TDD 사이클로 조율한다. 진입점은 `/cue` 하나다.

**비전**: 모든 코드 변경이 *실패하는 테스트*에서 출발해, 짧은 피드백 루프로, 품질이
점진적으로 좋아지게 만든다. 추측하지 않고, 막히면 멈춘다.

> 절차의 상세는 이 스킬이 아니라 `docs/`에 있다. 스킬은 분류·라우팅·공통 규칙만 담는다.

## 공통 규칙 (전 모드)

1. **테스트 가능한 로직은 실패 테스트(RED) 없이 금지.** 단순 SwiftUI 뷰·테스트
   불가능한 I/O 글루는 RED 면제 — 빌드·실행으로 검증. → `docs/tdd.md`
2. **한 사이클 = 한 커밋.** 사이클 30초~5분, 10분 넘으면 더 잘게 쪼갠다.
3. **테스트 코드는 반드시 작성한다 — 통과 여부는 묻지 않는다.** 테스트 가능한
   로직엔 테스트를 작성하되, 빌드·테스트 통과 여부를 작업 중 사용자에게 되묻지
   않는다. 작성까지가 하네스의 몫. 검증은 push 직전에 모아서 한다 (→ Step 5).
4. **디자인 시스템 규칙** → `docs/design-system.md`
   - 색은 Apple 시스템 컬러(`.primary`/`.secondary`/`.tint`/`Color.red` 등)만 — 자체 색 토큰·hex·OKLCH·RGB 리터럴 금지.
   - 폰트는 `AppFont`, 간격은 `Spacing` 토큰만 — 고정 숫자 직접 입력 금지.
   - iOS 퍼스트파티 컴포넌트 우선.
   - 커스텀 컴포넌트는 **만들기 전 반드시 사용자에게 알리고 합의**한다.
5. **의존성 규칙** — `Domain`은 `SwiftUI`·`SwiftData`를 모른다. → `ARCHITECTURE.md`
6. **빌드·테스트 실행은 사용자가** 한다. 하네스는 코드(테스트 포함)까지만 —
   "빌드 됐나요·테스트 통과했나요"를 묻지 않는다.
7. **모호하면 추측 금지 → 되묻는다. 막히면 멈춘다.**
8. **push는 사용자 승인 후.**

## Step 1 — 모드 분류

자연어 의도 + git/빌드 상태로 4모드 중 하나를 고른다. 모호하면 되묻는다 (추측 금지).

| 모드 | 트리거 | 절차 문서 |
|---|---|---|
| **feat** | "추가", "기능 만들어", "Scene 추가" | `docs/workflow/feat.md` |
| **fix** | "고쳐", "버그", "작동 안 함" (원인 알 때) | `docs/workflow/fix.md` |
| **refactor** | "정리", "리팩토링", "구조 개선" | `docs/workflow/refactor.md` |
| **debug** | "왜 이래", "원인 찾아", "이상해" (원인 모를 때) | `docs/workflow/debug.md` |

인자 없이 `/cue`만 오면 git/빌드 상태로 다음 행동을 추론한다.

## Step 2 — 상태 확인

- 개발은 `develop` 브랜치에서 진행한다. **기능별 브랜치를 따로 만들지 않는다.**
- 미커밋 변경·실패 테스트 유무를 확인하고 그에 맞게 라우팅한다.

## Step 3 — 모드 실행

분류된 모드의 워크플로 문서를 열고, 그 절차대로 TDD 사이클을 진행한다.
사이클 변형:

- **feat** — `plan → red → green → refactor → green` (plan 합의 없이 코드 진입 금지)
- **fix** — `(debug 진단) → refactor=수정 → verify`
- **refactor** — `커버리지 확보 → refactor → green`
- **debug** — `재현 → 실패테스트(red) + 원인 진단` → 멈춤 (안 고침)

### 모드 조립 — debug 서브루틴

debug는 어느 모드 안에서든 호출되는 진단 서브루틴이다:

- feat / fix / refactor 진행 중 **예상 밖 실패**를 만나면 → 현재 모드를 일시중단하고
  debug로 들어간다 → 원인 + 재현 테스트 확보 → 중단했던 모드로 복귀.
- 호출 스택처럼 동작한다. 현재 모드와 중단된 모드를 기억한다.
- debug → fix는 그대로 버그 파이프라인이다.

## Step 4 — 검증

하네스는 코드와 테스트를 **작성하기만** 한다. 빌드·테스트는 사용자가 직접 돌리며,
**작업 중 그 결과를 사용자에게 요청하지 않는다** — 사이클마다 멈춰 "빌드 됐나요·
테스트 통과했나요"를 묻지 않고 다음 작업으로 이어간다. 검증은 push 직전에 모아서 한다.

## Step 5 — 마감

한 사이클 = 한 커밋. 접두사 `feat:` / `fix:` / `refactor:` (debug는 fix에 흡수).

**push 전 점검 (필수)** — push하기 전에 **전체 테스트 코드의 로직을 처음부터 끝까지
점검한다**: 각 테스트가 의도한 동작을 정확히 검증하는지, 이번 변경이 만든·바꾼
코드를 테스트가 커버하는지, 깨지거나 낡은 테스트가 없는지. 점검을 마친 뒤 push한다.

push는 사용자 승인 후.

## 멈춰야 할 때

- 모드 분류가 모호 → 사용자에게 되묻는다.
- feat의 plan에 열린 질문·블로커가 남음 → red로 진입하지 않는다.
- 커스텀 컴포넌트가 필요 → 만들기 전에 사용자에게 알리고 합의한다.
- 사이클이 10분 초과 → 요구사항을 더 잘게 쪼갠다.
- 재현 안 되는 버그·빌드 환경 문제 → 사용자에게 에스컬레이션한다.
